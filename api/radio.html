Radio inputs, accumulation and propagation

Radio interfaces consume completed tracks. Host interfaces manage input lifetime and output completion, while numerical projection functions operate on borrowed records and waveform arrays. The declarations below are generated from the public headers at the baseline recorded in API reference.

Read Track collection and observer preparation for track collection and observer preparation, Parallel projection and waveform accumulation for execution and accumulation, and Propagation models and medium-specific interfaces for ordinary, geometrical-optics and full-wave propagation. The separate propagation interfaces have different input and output contracts.

Track conversion and observer configuration

The native-step adapter converts a completed electron/positron segment into the standard projector record. It is not a particle-transport operation. Observer positions and track positions must share the configured coordinate system; observer times use seconds and sampling rates use Hz. Constructing RadioConfig does not initialize an accumulator or transfer arrays.

Sources: HostRadioRecord.hpp, RadioObserverSnapshot.hpp and RadioConfig.hpp.

Host dispatch and resident accumulation

IRadioBackend accepts borrowed host tracks and requires their contents to be copied before submission returns. Download completes pending input, including a final partial batch. Its historical gpuRadioEnabled name reports whether the implementation accepts these records; it does not require CUDA or even a GPU execution space.

RadioAccumulator owns ordinary CoREAS/ZHS storage in one execution space. Host submission copies input; resident submission borrows the supplied device view. The runtime, accumulator and device input allocations must remain valid until submitted work completes. Use the same execution instance for dependent operations. The reference below lists consumer lifecycle methods, excluding the public projection helpers exposed for compiler implementation constraints.

Sources: IRadioBackend.hpp and RadioAccumulator.hpp.

class IRadioBackend

Host dispatch interface for a configured radio calculation backend. A backend owns its propagation model, geometry and observer data; this interface does not require a height table or a particular material. Records use the backend’s configured common coordinate system and units. enqueueRadioTracks must copy records before returning. downloadRadioWaveforms completes pending work, including a partial final batch, before returning. CoREAS field and ZHS potential samples retain RadioWaveforms’ conventions.

Calls execute on the host. Implementations may dispatch Kokkos kernels with their own device-compatible propagation data, including complex geometries. This is an extension contract, not an implementation of firn ray tracing. Each instance is used by one shower owner; concurrent calls are not implied.

Subclassed by corsika::kokkos::radio::BorrowedRadioBackend< TBackend >

Returned samples

The ordinary CoREAS array contains electric-field samples; the ZHS array contains vector-potential samples. Native output performs the required adjacent-sample differentiation for ZHS. A component vector alone carries neither observer position nor its sample grid: retain the matching observer configuration and ordering. Firn accumulators below return their own spectral records rather than this ordinary waveform container.

Sources: RadioWaveform.hpp and RadioWaveforms.hpp.

Firn propagation interfaces

The geometrical-optics accumulator accepts tracks, solves the configured exponential-profile paths and accumulates the selected emission response. The full-wave accumulator instead consumes subdivided segments and a matching external response table. Both are host-facing interfaces with execution-space work behind them; their factory signatures expose the required inputs. Factories do not establish support for arbitrary optical profiles or geometry.

Runtime acquisition is lazy. If an EM runtime is borrowed, it must outlive the accumulator. Use and destroy these interfaces on the coordinating host thread. The propagation chapter specifies table coverage, branch handling, source formalism and finalization, which remain necessary when interpreting a downloaded spectrum. Sources: IGeometricalOpticsAccumulator.hpp and IFullWaveAccumulator.hpp.

class IGeometricalOpticsAccumulator

Batched GO with device ray solving and coherent spectra. Input tracks and the unchanged subdivision controller stay on the host. Ray records remain in the execution space; compact summaries supply the host controller and diagnostics. The paths() audit API returns full records. Geometry and emission run in the selected Kokkos execution space. Frequency-domain outputs visit tracks in input order; time-domain emission retains its atomic accumulation. Runtime acquisition is lazy; an EM runtime is borrowed when available and must outlive this object. Use on the coordinating host thread.

class IFullWaveAccumulator

Ordered schema-2 full-wave projection behind a host-only interface. Kokkos owns device buffers and execution. Each observer/frequency pair owns its spectrum bins and traverses input segments in order; no floating-point atomic sum or implicit out-of-table propagation model is used. Construction validates host table data; the first nonempty flush acquires the runtime and allocates device storage. An existing EM runtime is borrowed and must outlive this accumulator. Otherwise radio owns initialization. Construct, use and destroy the accumulator on the coordinating host thread.
