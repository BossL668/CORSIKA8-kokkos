Runtime and execution interfaces

These interfaces are called on the host. They select or own execution resources, submit numerical work and coordinate native completion. Their presence in a public header does not make their methods device-callable. Declarations are generated from the reference headers identified in API reference.

The lifecycle contracts are in Runtime selection and ownership; queue and return semantics are in Batch execution and CPU return paths and Hybrid event execution. Runtime configuration, particle scheduling and process coordination are separate responsibilities.

Execution configuration and ownership

RuntimeConfig selects a compiled backend, visible device, host threads and tuning policy. Cooperative fields apply only to the explicitly supported cooperative path; they do not independently enable a hybrid application. BackendRuntime owns the production backend’s process lifetime, with a restricted cooperative lease. The generic Runtime below has a different sharing/borrowing contract and is not a replacement owner for BackendRuntime.

Sources: RuntimeConfig.hpp and BackendRuntime.hpp.

class BackendRuntime

Process-level Kokkos lifetime, with an explicit internal cooperative lease.

Independent builds contain OpenMP or one GPU with a Serial host. The experimental CUDA_OPENMP build normally selects one execution space; ordinary CUDA mode still initializes OpenMP with one thread. An explicitly cooperative owner may instead lend the process lifetime to CUDA/OpenMP instances on the same coordinator thread. All instances and the final lease must be destroyed on that thread, after their views and work finish. This lifetime facility alone does not enable a cooperative air shower.

The generic runtime manages or borrows the build-selected default execution space. Views and execution-space objects must be released before its final owning reference. Its accessors report configuration; they do not advance particles. Source: Runtime.hpp.

class Runtime

Manage or borrow the single Kokkos runtime of this process.

The first instance initializes Kokkos if necessary. Subsequent instances share its lifetime; the last instance finalizes only an initialization owned here. An externally initialized runtime is borrowed and is never finalized here. Kokkos cannot be initialized again after finalization.

Construct and destroy all instances on the coordinating host thread. An external initialization must also belong to that thread and outlive all instances. Destroy all Kokkos Views and execution-space objects before releasing the last instance. Destruction on another thread is a contract violation and terminates the process.

This class neither selects a physics backend nor schedules particles. The default execution space is selected when building the Kokkos dependency.

Public Functions

explicit Runtime(int numThreads = 0, int deviceId = -1)

Initialize Kokkos, or acquire a compatible existing runtime.

Parameters:

  • numThreads – Host parallel-backend thread count; zero leaves the Kokkos default/environment setting unchanged, or accepts an existing runtime. This is not the number of CUDA threads.

  • deviceId – Visible GPU index; minus one leaves the default unchanged or accepts an existing runtime. CPU-only builds reject explicit device indices.

Throws:

  • std::invalid_argument – Invalid parameters or incompatible configuration.

  • std::logic_error – Reinitialization or acquisition on another host thread.

Backend submission interface

IEmBackend is the router’s host-facing contract for resident wavefronts, capacities, pending work, CPU returns and downloaded observables. A wavefront call can advance multiple physical steps; it is not a one-particle kernel launch. Input ownership, history allocation and completion semantics are specified in Batch execution and CPU return paths.

The independent-subshower methods are opt-in host coordination capabilities. They must not be interpreted as a persistent per-particle task queue inside one GPU. See Execution granularity and algorithm ownership.

Reusable production session

EmRunSession exports and uploads native model data on initial use, then resets event state for compatible subsequent showers. SessionBeginResult borrows the backend; the session owns it. Reuse is not general model/scene reconfiguration: changed environment data is rejected and changed calculators are not re-exported on the reuse branch. Follow the fresh-process and runtime-ownership guidance in Extending models and execution paths.

Source: EmRunSession.hpp.

class EmRunSession

Production run-level session: export/upload once and reset shower-local state. The caller retains the native calculators and host environment owners; the backend owns its synchronous device upload. Environment changes are rejected on reuse, as in production. This class does not reschedule particles.

Hybrid cascade coordination

HybridCascade coordinates scalar C8 work with an optional EM router and hadronic worker pool. The referenced environment, sequence, stack, output, router and pool remain caller-owned. Deferred states stay suspended until their corresponding results are committed. The scheduling and completion rules are in Hybrid event execution.

Source: HybridCascade.hpp. The EM router itself is declared in EmRouter.hpp and implemented in the matching .inl; its data exchange contract is described in Batch execution and CPU return paths.

template<typename TTracking, typename TProcessList, typename TOutput, typename TStack, typename TEmRouter = DisabledHybridEmRouter>
class HybridCascade

Coordinate scalar transport, an optional EM router and hadronic workers.

The native stack owns particles throughout scheduling. An EM router may stage supported histories; deferred hadronic projectiles remain suspended until their ordered final states are committed through the native secondary process chain. Referenced environment, processes, stack, router and pool must outlive this object.

Multi-process coordination

The coordinator operates before a local Kokkos context is created. It starts worker binaries, assigns static frontiers and validates/merges closed outputs. CoordinatorOptions is the library configuration record; command-line parsing can resolve different defaults before invoking run. The coordinator’s run function returns no scientific result object: its results are the output files and completion metadata described in Process coordination and worker lifecycle and Outputs and run checks.

Source: AirShowerCoordinator.hpp.
